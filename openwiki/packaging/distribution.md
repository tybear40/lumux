# Packaging and Distribution

Lumux distributes as a Python application under the app id **`io.github.enginkirmaci.lumux`** (v0.6.2, MIT license, Python ≥ 3.10). The primary channel is **Flathub** (`flatpak install flathub io.github.enginkirmaci.lumux` — README badge + install section); the repo itself is the build source for the Flatpak manifest.

## pyproject.toml

`[project]` declares the package metadata: version 0.6.2, MIT, authors, and seven runtime dependencies — `PyGObject>=3.42`, `zeroconf`, `urllib3`, `numpy>=1.24`, `Pillow>=10`, `requests`, `pydbus`. Dev extras add `pytest`, `pytest-asyncio`, `ruff` (line-length 88). The console script `lumux = "lumux.__main__:main"` is what both the desktop entry and the Flatpak `command` invoke.

Build config is a classic **src layout** via setuptools: `package-dir = {"" = "src"}` with `packages.find` under `src/`. `[tool.setuptools.data-files]` installs four data assets into FHS paths (`share/lumux/data`, `share/applications`, `share/metainfo`, `share/icons/hicolor/scalable/apps`), which is how a plain `pip install` still gets the desktop entry, metainfo, default settings, and app icon.

## Flatpak manifest

`flatpak/io.github.enginkirmaci.lumux.yml` targets `org.gnome.Platform` **50** (providing GTK4/libadwaita, GStreamer, and PyGObject) with `command: lumux`. Its `finish-args` encode the exact runtime capabilities the app needs:

| Permission | Why |
|---|---|
| `--socket=wayland`, `--socket=fallback-x11`, `--device=dri`, `--share=ipc` | UI; the Wayland socket is what the XDG ScreenCast portal requires |
| `--share=network` | Hue bridge mDNS discovery (zeroconf) and HTTP/DTLS control |
| `--filesystem=xdg-run/pipewire-0` | PipeWire node socket used by portal (pipewiresrc) capture |
| `--talk-name=org.kde.StatusNotifierWatcher` / `org.freedesktop.StatusNotifierWatcher` / `org.freedesktop.Notifications` | System tray via StatusNotifierItem on both KDE and freedesktop implementations, plus notifications |

There is no host filesystem, no `--socket=x11`-only bypass, and no host monitor access — consistent with the portal-first capture design (see [Screen Capture](../pipeline/screen-capture.md)).

The `lumux` module installs with `pip3 install --no-deps --no-build-isolation --prefix=/app .`, then copies the desktop entry, metainfo, and SVG icon into `/app/share`. A sibling module `python3-modules.json` — generated by **flatpak-pip-generator** — vendors the Python dependencies **offline**: each module pip-installs from a local wheel directory with `--no-index --find-links=file://… --no-build-isolation` (modules: pybind11, zeroconf, urllib3, numpy, Pillow, requests, pydbus). `--no-deps` on the app install is safe only because this vendored module list is complete.

## Desktop entry and AppStream metadata

`data/io.github.enginkirmaci.lumux.desktop` is a minimal entry: `Exec=lumux`, `Icon=io.github.enginkirmaci.lumux`, `StartupWMClass=io.github.enginkirmaci.lumux` (so GNOME can match the window), `Categories=Utility;GTK;`, hue/ambilight keywords.

`data/io.github.enginkirmaci.lumux.metainfo.xml` (162 lines) is the AppStream component: summary/description, homepage + bugtracker + VCS URLs, six screenshots hot-linked from `assets/screenshots/` (main window, bridge, general, capture, zones, sync configuration), branding color `#ba85d5`, and a `<releases>` history of **eight releases from 0.1.0 (2026-01-30) to 0.6.2 (2026-07-16)** — the project shipped a release roughly every few weeks through mid-2026.

## The OpenWiki update CI workflow

`.github/workflows/openwiki-update.yml` is the only workflow in the repo. It runs **daily at 08:00 UTC** plus on `workflow_dispatch`, with `contents: write` and `pull-requests: write` permissions. Steps:

1. Checkout with `fetch-depth: 0` — full history is required so `openwiki code --update` can diff HEAD against the commit it last documented (a shallow clone hides that commit and produces an empty change summary).
2. Node 22, then `npm install --global openwiki@0.9.0 mermaid@11.16.0 jsdom@…` (mermaid/jsdom only add diagram validation).
3. Run `openwiki code --update --print` with `continue-on-error: true`; model/provider/LangSmith credentials come from repo secrets (`OPENWIKI_PROVIDER=openai`, `OPENWIKI_MODEL_ID=gpt-5.6-terra`).
4. Delete transient `openwiki/.run.json`, then create a PR on branch `openwiki/update` staging `openwiki/`, `AGENTS.md`, the workflow file, and `CLAUDE.md` **only if it exists** (git add fails on a missing path and would stage nothing).
5. On a `failure` outcome the PR intentionally preserves only the pages completed before the failure, and the workflow exits non-zero to surface it.

This is the maintenance process behind this wiki: source changes accumulate, the daily run regenerates affected pages, and merging the PR baselines them.
